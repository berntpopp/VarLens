# Re-review: feat/chr-naming-per-build after fixes (3db537b2..HEAD)

What this change does: the fixes compute where shared notes go from each case's final names (`annotation-remap.ts`, both backends). They confirm builds in one batched write, with an audit row, a preselected build and a virtual list. They check free space and the WAL checkpoint before the SQLite backup. The PG job is split into three phases (plan, then move notes, then rename) and asks for one cohort rebuild at the end. **Must fix**
1. **PG: notes go missing or attach to the wrong case while the job runs** (`postgres-contig-naming.ts` `moveAnnotations` → `renameOneCase`). Phase 2 moves the notes of every planned case at once. Each case's variants keep their old name until phase 3 reaches that case, which can be hours later. Every read and filter joins notes on the exact name (`va.chr = v.chr`, e.g. `postgres-variant-clinical-filter-sql.ts:131`). Ran it: GRCh38 A `1:300` (only A) and `1:100` (shared with GRCh37 B). In the window, A shows no note at 300, so starred, ACMG and commented filters drop it. The user edits 100 and adds a note at 300 again. After the job: A shows the old notes, B shows A's edit, and the re-added `1:300` row has no user left (orphaned forever). The banner talks only about "cohort counts", so it is not honest about this. **Leanest fix:** delete phase 2 and the `annotations_moved` column. Remap inside each case's own rename transaction. `newName` = this case's pairs; other pending cases keep their current name, except a case whose current key at this locus is one of this case's targets and that renames away (a swap or chain; repeat until stable, about 6 lines in `remapAnnotationGroup`). Edits made before the rename then move with the case. Only real swap loci, which are rare, are moved early. SQLite stays as it is (one transaction). Add the window test above; the current "edit during the job" test edits *before* phase 2, so it misses this.

**Should fix**
2. **A failing job looks like "in progress" forever** (`scheduleContigNaming`). The back-off (5 min doubling to a 6 h cap) is bounded and logs each attempt. But `planOneCase`/`renameOneCase` always take the lowest `case_id` first, so one case that fails every time stops the whole queue. The user only sees "being updated". Fix: return `renameFailed` (true when `failures` has the schema) from `listBuildReviews` and show it in the banner.
3. **Free-space check can block opening on an odd filesystem.** `statfsSync` exists on Linux, macOS and Windows (Node ≥ 18.15; on Windows `bavail × bsize` is the free space of the caller). The ratio and directory are right. But a throw from `statfsSync` (e.g. some network shares) aborts the migration with a raw error. Fix: catch it and skip the check (the ENOSPC abort is still safe).

**Nice to have**
4. The PG phase 2 is one transaction for all 10k cases and locks every note on the renamed spellings, so note edits wait while it runs. Fix 1 removes this.
