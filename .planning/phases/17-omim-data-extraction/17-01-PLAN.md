    - AFTER UPDATE trigger: Add `old.omim_mim_number` to delete-insert, `new.omim_mim_number` to re-insert

    e) **initializeSchema**: Update to handle FTS5 rebuild for existing databases that now have the omim_mim_number column (from migration) but whose FTS5 table was created without it. The logic:
    - After `migrateVariantsTable(db)`, check if the variants_fts table exists and what columns it has
    - Use a helper: query `PRAGMA table_info(variants)` to check if omim_mim_number column exists
    - If the column exists, DROP the old FTS5 table, triggers, and recreate with the new definition that includes omim_mim_number
    - Then repopulate FTS5: `INSERT INTO variants_fts(rowid, gene_symbol, consequence, omim_mim_number) SELECT id, gene_symbol, consequence, omim_mim_number FROM variants`
    - If the column does NOT exist (very old database where migration somehow failed), just create FTS5 without omim_mim_number (backward compatible)

    IMPORTANT: The FTS5 table uses `CREATE VIRTUAL TABLE IF NOT EXISTS` which means it won't recreate if it already exists with the old schema. You MUST explicitly DROP it first when upgrading. Use this approach in initializeSchema:
    ```typescript
    export function initializeSchema(db: Database.Database): void {
      db.exec(createTables)
      migrateVariantsTable(db)
      db.exec(createIndexes)

      // Rebuild FTS5 to include any new columns (e.g., omim_mim_number)
      // DROP first since IF NOT EXISTS won't update existing table structure
      db.exec('DROP TABLE IF EXISTS variants_fts')
      // Also drop triggers that reference the old FTS table
      db.exec('DROP TRIGGER IF EXISTS variants_fts_ai')
      db.exec('DROP TRIGGER IF EXISTS variants_fts_ad')
      db.exec('DROP TRIGGER IF EXISTS variants_fts_au')

      // Check if variants table has omim_mim_number column
      const columns = db.prepare('PRAGMA table_info(variants)').all() as { name: string }[]
      const hasOmim = columns.some((c) => c.name === 'omim_mim_number')

      if (hasOmim) {
        // Create FTS5 with omim_mim_number
        db.exec(createFTSTable)
        db.exec(createFTSTriggers)
        // Repopulate FTS5 index from existing data
        db.exec(`
          INSERT INTO variants_fts(rowid, gene_symbol, consequence, omim_mim_number)
          SELECT id, gene_symbol, consequence, omim_mim_number FROM variants
        `)
      } else {
        // Legacy database without omim column -- use old FTS structure
        db.exec(createFTSTableLegacy)
        db.exec(createFTSTriggersLegacy)
        db.exec(`
          INSERT INTO variants_fts(rowid, gene_symbol, consequence)
          SELECT id, gene_symbol, consequence FROM variants
        `)
      }
    }
    ```
    Add `createFTSTableLegacy` and `createFTSTriggersLegacy` as copies of the OLD FTS5 SQL (without omim_mim_number) for backward compatibility. This is the safest approach.

    CRITICAL: The FTS5 repopulation must happen AFTER creating triggers. Actually -- triggers fire on INSERT into the VARIANTS table, not on direct INSERT INTO variants_fts. The repopulation INSERT goes directly into variants_fts, so trigger order doesn't matter. But to be safe: create FTS table first, repopulate, THEN create triggers (triggers are for future inserts/updates/deletes on the variants table).

    Corrected order:
    1. DROP old FTS table and triggers
    2. Create new FTS table
    3. Repopulate FTS index from existing data
    4. Create new triggers (for future changes)
